## 一、总览

把设计稿里的 6 大功能模块，拆成 **7 个阶段（P0–P6）**，每个阶段都能独立产出可体验版本。

| 阶段 | 主题 | 覆盖模块 | 规模 | 前置依赖 | 里程碑 |
|:---:|---|:---:|:---:|:---:|---|
| **P0** | 技术验证 PoC | — | S | 无 | M0 技术路线确认 |
| **P1** | 进程净化（MVP） | M2 | L | P0 | M1 可一键净化的可用版 |
| **P2** | 开机加速 | M1 | M | P1 | M2 开机耗时可视化 |
| **P3** | 场景模式引擎 | M3 | L | P1、P2 | M3 三套场景可切换 |
| **P4** | 一键体检 + 垃圾清理 | M4、M5 | M | P1 | M4 完整优化闭环 |
| **P5** | 监控悬浮球 + 打磨 | M6 | M | P1 | M5 Beta 版 |
| **P6** | 发布加固 | — | M | P5 | M6 1.0 正式版 |

**规模说明**：S = 单点验证，M = 一个完整功能页，L = 跨模块的完整子系统。

### 排序依据

1. **技术风险前置**：Win32 调用能力与打包体积是整个方案的地基，P0 必须先证伪/证实，避免后期返工。
2. **用户感知优先**：进程净化和开机加速是用户最能直接感受到价值的两个点，紧接 P0 之后做。
3. **差异化靠后**：场景模式是护城河，但它依赖 P1/P2 沉淀的进程与服务控制能力，故排 P3。
4. **每阶段可交付**：不做"半年后见"的大爆炸式开发，每阶段结束都有可运行版本。

#### 判定质量的实测结论（重要）

在 255 个真实进程上，判定引擎只标出 **1 个**「可安全结束」。
这是**刻意为之**：产品原则是「宁可少杀，不可错杀」，引擎设了 8 道封顶条件，
任何一条命中都不得判 `Safe`。

由此得出一个必须写进 UI 文案的产品结论：

> **在正常桌面系统上，「可以安全杀掉的进程」是个位数。
> 用户可感知的收益主要来自工作集裁剪（实测 1.1 GB），而非结束进程。**
>
> UI 不能夸大「清理进程」的收益，否则就是在骗用户。

#### 零误杀怎么验：`PurgeMode::DryRun`

「200 次净化零误杀」这条标准有个天然陷阱：**如果验证手段是真的去杀进程，
那验证过程本身就成了最大的风险源**。所以引擎把「判定」和「执行」彻底拆开：

```rust
PurgeEngine::new()   // Live   —— 生产路径，真实执行
PurgeEngine::dry()   // DryRun —— 只算不做，零系统改动
```

`DryRun` 会完整跑完采集 → 判定 → 全部安全校验 → 收益估算，
把「打算结束谁、打算裁谁」如实算出来，但**不调用任何系统写操作**，
也不落快照。压力测试因此可以放心跑满 200 轮：

```bash
old666-poc --stress 200
```

底层还有一道编译期就定死的熔断（`core::safety`）：
`cargo test` 构建下 `dry_run` **默认开启**，
也就是说**测试用例在结构上不可能结束真实进程** ——
不依赖写测试的人记得加保护。

#### 写操作默认关闭

PoC 的所有写操作（结束进程 / 工作集裁剪）**默认跳过**，
必须显式传 `--allow-write` 才执行；执行时用 PID 白名单闸
把范围锁死在自己拉起的子进程上，执行完立即撤销。

```rust
safety::set_kill_allowlist(Some(children + self_pid));
// …只可能动这几个…
safety::set_kill_allowlist(None);
```

即便后续代码写错 PID，`killer` 的写操作也杀不到任何用户进程。

> **红线**：任何结束进程的操作都必须先向用户出示目标清单并获得明确确认。
> 规则详见 `.workbuddy-ai/skills/kill-process-confirmation/SKILL.md`。

- [x] 禁用执行器（注册表值、启动文件夹快捷方式、SERVICE_DISABLED、schtasks /DISABLE）
- [x] **延迟启动**执行器（服务「延迟自动启动」，2026-10-15）

- [x] 历史开机耗时趋势记录（取事件日志最近 50 次开机）
- [x] **选中交互修复**：全选/单选热区、跨筛选一致性、推荐项一键选中（2026-10-15 二轮）
- [x] **启动项进程知识库**：内置 173 条 + 用户可编辑（外置 JSON，优先级更高）
- [x] **白名单 / 黑名单**：黑名单免二次确认直接禁用（外置 JSON）
- [x] **禁用项保留在列表** + 单条一键启用（不再从列表消失）
- [x] **注册表项删除**（仅 Run 键 / 启动文件夹，删除前自动备份原值）
- [x] 对标 360 安全卫士启动项管理的功能点覆盖（见技术说明 §十二）

**交付物**：开机加速页（`src/boot.js`）+ `core/boot.rs`、`core/startup*.rs`

**实际做法与实测数据**

- **采集不走 ETW 会话**，改为读系统自带的开机性能诊断日志
  `Microsoft-Windows-Diagnostics-Performance/Operational`（事件 100 = 本次开机总账，
  101/102/103/109 = 被点名的拖慢对象）。好处：不用常驻 ETW 会话、不抢 CPU，
  坏处：没有实时性，本次开机要等下一次开机才看得见 —— 在 UI 上如实说明。
- **归因误差 0%**（验收标准是 <10%）：各阶段耗时全部采用 Windows 自己上报的数字，
  无法归入已知阶段的残差单独作为「主路径其他开销」一段显示，
  于是 `Σ 阶段 == BootTime` 恒成立，由测试 `record_splits_phases_and_sums_exactly_to_main_path`
  锁死。这是把"估得准"换成"算得对"——不丢信息，也不造假。
- **真机 8 次开机**：最快 31.8 s / 均值 61.0 s / 最慢 108.1 s；
  最近一次 105.8 s（主路径 18.5 s + 桌面后台 87.3 s），
  拖慢对象 `WorkBuddyAI.exe` 拖慢 54.1 s、`WorkBuddy.exe` 20.4 s。
- **启动项 148 项**（注册表 16 / 启动文件夹 1 / 自动服务 105 / 计划任务 26）。
  分级后：危险 101（服务默认保守）、可安全禁用候选 11。
- **两段式扫描**：快速扫描 154 ms 先出列表（28 项发布者待确认），
  补签 745 ms（这 16 个文件合计 601 MB，串行比并行更快——实测 8 线程 2.1 s vs 单线程 0.6 s，
  瓶颈是磁盘 I/O 争抢）。首屏体感与判定质量都不牺牲，
  等价性由测试 `fast_then_verify_equals_deep` 保证。
- **写操作安全**：`check_startup_change`（本次允许清单 + 熔断器双闸）→
  前端先跑 `startup_plan` 把真实演练清单摆给用户 → 用户确认后才 `startup_apply`；
  撤销载荷自包含（注册表原值 / 服务原 Start 值 / 任务原启用状态），换机器也能还原。
  关闭服务走 `ChangeServiceConfigW(SERVICE_DISABLED)` 而非直接写注册表，否则 SCM 不会收到通知。
- **延迟启动**（2026-10-15 补齐）：`ChangeServiceConfig2W(SERVICE_CONFIG_DELAYED_AUTO_START_INFO)`，
  同样走 SCM 不写注册表。边界：**只对自动启动（Start=2）服务有意义**，下次开机生效，
  注册表项/启动文件夹/计划任务没有等价能力，逐条明确拒绝而不是假装做了点什么。
  与「禁用」是两种用户意图，UI 拆成两个按钮、两套确认文案。
  真机实测（`tests/service_write_verify.ps1`，自建临时服务 old666_delay_probe，测完删除）：
  延迟 3/3 生效（注册表 `DelayedAutostart` 0→1）、回滚 3/3 复原；
  禁用→回滚 1/1（Start 2→4→2）。
- **前端无头验证**：`tests/frontend_boot.mjs` 用真机 fixture 跑断言全绿
  （分段条/图例/趋势/归因/两段式补签/筛选/搜索/禁用与延迟两套确认弹窗/还原入口），
  过程中揪出并修掉多个真 bug（见 README「重要结论」）。

**二轮（2026-10-15）：可用性返工 —— 用户反馈「不好用，一堆 bug」**

用户的原始反馈逐条落地，根因都不在逻辑层，而在**交互细节与知识覆盖面**：

- **「全选点了没反应/勾不上」** —— 根因是**热区**：全选框当时只是工具栏里一个
  15×15 的裸 checkbox，且落在首屏视口之外。改成 `label.chk` 包裹整块热区
  （实测 60×33），行内勾选热区 28×32；并把「全选」语义钉成
  「勾上**当前筛选内全部可勾选项**」，切换筛选后全选框自身状态与实际勾选必须一致
  （之前会出现「全选框显示已全选、列表里却有空勾」）。回归断言 12 条，直接量像素。
- **「推荐禁用的要支持一键选中」** —— 新增「一键选中推荐项」：
  推荐 = 可勾选 ∧ 风险档「可安全禁用」∧ 未加白。真机 148 项里命中 10 条。
  白名单里的条目会被排除（用户明确表态「这个我要留」）。
- **启动项进程知识库** —— 覆盖率从 **89/148（60%）提到 142/148（96%）**。
  分三层查找，逐层降级：① 显示名 + exe 基名 → ② 路径里的厂商/产品目录段
  （`path_hint`）→ ③ 兜底通配条目。第三层只在**前两层全落空**时才生效，
  且命中后建议被强制成「谨慎处理」——`xxxlauncher` 到底是游戏启动器还是
  厂商推广位，光看名字分不出来，说「可以禁用」是不负责任的。
  过程中抓到两个真误判：裸 key `launcher` 会把《三角洲行动》启动器判成
  「可以禁用」（会直接搞坏游戏，已删除该 key 并加回归测试）；
  `psspoolsv` 条目里重复的 `fax` key、Defender 的 `nissrv` 双条目导致匹配不确定。
- **白名单 / 黑名单**（外置 JSON `data/startup_lists.json`）——
  **黑名单免二次确认、直接禁用**（用户明确要求「加入黑名单的不需要过问直接禁用」）；
  白名单则把条目从「推荐禁用」里摘出去。名单按名称匹配，且**同时匹配显示名与
  exe 基名**（`hits()`）—— 否则用户填了 `ollama` 却因为显示名是
  `Ollama Server` 而没生效。
- **已禁用项保留在列表**（用户选择「保留在列表，可一键启用」）——
  注册表项走 `StartupApproved\Run` 二进制标志（`0x02` 启用 / `0x03` 禁用），
  条目**原地留在列表里**并带「老六禁用」标记；服务与计划任务禁用后本来会从枚举里
  消失，由 `merge_disabled_by_us()` 按我们自己的变更记录重建回来。
  单条恢复走行内「启用」按钮，**不弹确认框**（启用是非破坏性动作，
  `needs_risk_gate()` 对 `Mode::Enable` 直接放行）。
- **注册表项删除** —— 只对 `run_key` / `startup_folder` 开放；
  服务与计划任务在说明面板里明确拒绝并给出替代方案（「删掉会伤系统，请改用禁用」）。
  删除前自动备份原值，交给「变更记录」还原。取消逻辑由一条前端断言锁住。

**二轮验证**：Rust 单测 **160 项全过**；前端无头断言扩到 **101 项全过**
（新增第 9~15 组：选择交互（含热区像素）/ 一键选中推荐 / 知识库面板与编辑 /
**未收录条目的手动补充** / 白黑名单 / 单条启用 / 删除来源限制 / 设置抽屉）。

**未做的部分**：优化前后开机的**实测对比**需要用户真的点禁用并重启，属使用后验证。

**验收标准**

- [x] 时间线分段归因误差 < 10%（实测 0%，见上）
- [x] 所有禁用项可一键还原
- [x] 「推荐禁用」可一键选中并批量禁用
- [x] 每个启动项都有「是干什么的」说明（真机覆盖 142/148 = 96%，其余可手动补充）
- [x] 黑名单条目加入后免确认直接禁用
- [x] 被禁用的条目仍保留在列表中、可单条启用
- [x] 注册表项可删除，且删除前已自动备份原值
- [ ] 优化后开机时间有可测量的缩短（需要用户实际点禁用并重启后对比，属使用后验证）

- [x] 服务器模式零误杀，所有变更可追溯

**P3 落地现状（v0.1.4 开发中，2026-11-06）**

| 项 | 实现位置 |
|---|---|
| 规则 DSL（JSON） | `src-tauri/src/core/modes/*.json`（daily/game/server 三份内置规则） |

| 测试 | Rust 单测 202 全绿；`tests/frontend_mode.mjs` 无头前端 29/29 |

**安全设计**：结束进程的动作必须满足三件事才可能发生 ——
① 规则本身声明 `purge_processes`；② 用户在 UI 里点了确认（`mode_apply` 的 `kill_confirmed=true`）；
③ 后端 `mode_runner` 校验到 `kill_confirmed` 才放行。自动切换**只提示不执行**，不绕过任何一环。

**风险**：模式之间动作冲突（如游戏模式提优先级 vs 服务器模式保稳定）→ 引擎需明确的优先级与互斥声明。

## 六、安全红线

1. **任何结束进程的操作，都必须先向用户出示目标清单并获得明确确认。**
   代码层面的默认值必须是「关」，不能靠调用方记得关掉。
   规则详见 `.workbuddy-ai/skills/kill-process-confirmation/SKILL.md`。
2. **测试不得影响系统运行。** `cargo test` 构建下熔断默认开启，
   任何测试用例在结构上都不可能结束真实进程。
3. **裁剪与结束用不同的尺子。** 裁剪不终止进程，服务宿主类可以裁；
   但属于交互式程序的进程一律不裁（会造成用户切回时卡顿）。
4. **不虚报收益。** 演练文案必须写「预计」，不能写成「已释放」。
