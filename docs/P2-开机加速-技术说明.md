## 一、开机数据从哪来：不用 ETW，读开机诊断日志

最初的计划写的是「ETW 开机阶段事件采集」。实际落地后改为读系统自带的
**开机性能诊断日志**：

```
通道:  Microsoft-Windows-Diagnostics-Performance/Operational
查询:  EvtQuery(None, channel, "*", EvtQueryChannelPath | EvtQueryReverseDirection)
读取:  EvtNext → EvtRender(EvtRenderEventXml)
```

| 事件 ID | 含义 | 用途 |
|---|---|---|
| **100** | 本次开机总账 | 拆分出 11 个阶段的耗时 |
| 101 / 102 / 103 / 109 | 应用 / 服务 / 驱动 / 设备被点名拖慢 | 「谁在拖慢开机」卡片 |
| 104–108 | 后台维护（预取、SuperFetch 等） | **不是凶手，直接忽略** |

**为什么不用 ETW 会话**：ETW 实时会话要常驻内核态、拿管理员权限、抢 CPU，
而且用户装的是「优化工具」不是「性能分析仪」。事件日志的代价只是开机后
11 ms 的一次查询，缺点是要等下一次开机才看得见本次结果 —— 这一点在 UI 上如实说明。

> ⚠️ XPath 传空串会被判 `ERROR_EVT_INVALID_QUERY` (15001)，必须传 `"*"`。
> `EvtNext` 读完后返回 `ERROR_NO_MORE_ITEMTS` (259) 是正常终止，不是错误。

## 二、事件 100 的真实字段（按真机 XML 导出，2026-10-15）

拆分阶段**只认这些字段**，一个都不猜：

| 字段 | 归属阶段 | 可优化 |
|---|---|---|
| `OSLoaderDuration` | 引导加载（UEFI / 引导管理器） | ✗ |
| `OtherKernelInitDuration` | 内核初始化 | ✗ |
| `BootDriverInitTime` | 驱动加载 | ✓ |
| `BootDevicesInitTime` | 设备枚举 | ✗ |
| `BootSmssInitTime` | 会话管理器初始化 | ✗ |
| `BootCriticalServicesInitTime` | 关键服务启动 | ✓ |
| `BootMachineProfileProcessingTime` | 机器配置加载 | ✗ |
| `BootUserProfileProcessingTime` | 用户配置加载 | ✓ |
| `BootExplorerInitTime` | 桌面初始化 | ✓ |
| （残差） | 主路径其他开销 | ✗ |
| `BootPostBootTime` | 桌面就绪后的后台开销 | ✓ |

三个坑，都在真机上踩过：

1. **`BootKernelInitTime` 不是内核阶段**。真机实测只有 30 ms，
   名字看着像内核总耗时，其实是某个子项。拿它当「内核」会让归因彻底错位。
2. **降级标记字段叫 `BootIsDegradation`**，不是 `IsDegraded`。差一个字母静默失效。
3. **字段名会漂**。解析时不写死 schema，而是把 `<Data Name="X">v</Data>`
   全量抽成键值表后做归一化（小写 + 去掉空格 / 连字符 / 下划线）再查表 ——
   微软加字段、改字段都不至于让解析崩掉。

### 归因误差为什么是 0%

各阶段时长全部采用 Windows 自己上报的数字，**没有一个是估算的**。
无法归入已知阶段的残差（`MainPathBootTime - Σ已知`）单独作为
「主路径其他开销」一段显示，因此恒有：

```
Σ 所有阶段 == MainPathBootTime + BootPostBootTime == BootTime
```

这比「估得比较准」更实在：不丢信息，也不造假。
由测试 `record_splits_phases_and_sums_exactly_to_main_path` 与
`timeline_never_panics_and_is_self_consistent` 锁死。

### 拖慢对象如何对上是「本次」开机

最初按 `TimeCreated` 聚类，结果**每一次开机都挂着同一批凶手** ——
因为归因事件的记录时间和开机事件的记录时间本来就不重合。
正解是用事件 100 的 `BootStartTime` 与归因事件的 `StartTime`
做**字符串精确相等**匹配（这两个字段就是同一个值）。
改完后真机验证：最近一次开机 4 个凶手，上一次 1 个，不再串场。

## 三、启动项枚举的四个来源

| 来源 | 位置 | 禁用手段 | 撤销载荷 |
|---|---|---|---|
| 注册表 Run / RunOnce | HKCU/HKLM × WOW6432Node | 删/清值（备份原值） | `{reg: 原位置, value: 原值}` |
| 启动文件夹 | `.lnk` 目标 | 移入隔离目录 | `{path: 原路径}` |
| 自动服务 | 注册表 `Start == 2` 的键名（非枚举 SCM，826 条只花 36 ms） | `ChangeServiceConfigW(SERVICE_DISABLED)` | `{key: 键名, start: 原值}` |
| 计划任务 | `System32\Tasks` 的 XML，只取 Boot/Logon 触发器 | `schtasks /Change /TN <uri> /DISABLE` | `{uri, enabled: true}` |

几个坑：

- **关闭服务必须走 `ChangeServiceConfigW`**。直接改注册表 `Start` 值
  不会通知 SCM，要到下次重启才生效，甚至可能被 SCM 覆盖。
- **`location` 要能反写**。Run 键的 location 存成
  `HKCU\Software\...\Run!ValueName` 这种「位置 + 值名」的形式，
  还原时才知道删哪个值。早期的 `item.id` 是哈希，好看但不能反写。
- **禁用判定读 `StartupApproved\Run` 二进制的首字节最低位**（1 = 已禁用），
  而不是「值存不存在」。
- **服务显示名可能是间接字符串**（`@%SystemRoot%\...dll,-100`），
  用 `SHLoadIndirectString` 解；解不出就退回原始值，不猜。
- **image path 前缀要按前缀剥**：`\??\` → `\SystemRoot\` → `\System32\`。
  曾经用 `.replace()` 全量替换，结果 `C:\Windows\System32\...`
  被二次包裹成 `C:\WindowsC:\Windows\System32\...`。

## 四、两段式扫描：为什么拆成两步

148 个启动项里只有 **28 个**需要读文件验签（其余靠名称与路径就能定级），
而这 28 个对应 **16 个不同文件、合计 601 MB**（LM Studio 200 MB、
WorkBuddyAI 195 MB、FeverGames 77 MB）。

| 方案 | 首屏耗时 | 结论 |
|---|---|---|
| 一次性深扫 | 745–820 ms | 首屏明显卡顿 |
| 8 线程并行验签 | **2.1 s** | 比串行还慢 —— 601 MB 读取是磁盘 I/O 瓶颈，线程只会争抢 |
| **快速扫描 → 按需补签** | **154 ms** + 745 ms | 首屏先出列表，补签在后台完成 |

判定质量与速度并不冲突，前提是两步**完全等价**：

```rust
scan_with(false) + verify_pending(None)  ≡  scan_with(true)
```

这个不变式由测试 `fast_then_verify_equals_deep` 逐字段（含顺序）断言。
补签只处理**当前可见**的 id：用户筛到「服务」时就只补那 105 条，
不会为一个折叠起来的 200 MB 可执行文件白读一遍。

> 补签曾经丢掉「登录触发；」这类理由前缀、以及列表排序 —— 都是被这个
> 等价性测试抓出来的。**没有等价性测试的优化等于裸奔。**

## 五、风险分级：宁可少关，不可错关

分四档：`Safe`（可安全禁用）/ `Caution`（谨慎）/ `Dangerous`（不建议，唯一不可禁用）/
`Unknown`（无法判定）。三条设计原则：

1. **必备词表约 60 条**：Defender、加密、音频、输入法、触控板、GPU 驱动、
   RPC/DCOM/DHCP/DNS/打印/Shell/搜索/字体/WMI/WinUpdate/Installer ——
   命中一律不给「可安全禁用」。
2. **匹配「显示名 + exe 基名」，不匹配整条命令行**。否则 `power`
   会命中 `powershell`、`amd` 会命中 `amd64`，误伤一大片。
3. **可疑特征只降不升**：`\Temp\`、`-encodedcommand`、`-windowstyle hidden`、
   `powershell`/`mshta`/`rundll32`/`wscript`/`regsvr32` 只能把 `Safe` 压回
   `Caution`，**绝不升级为 `Dangerous`** —— 用户自己写的启动脚本不该被骂成病毒。

真机分级结果：148 项中 `Dangerous` 101（自动服务默认保守，宁枉勿纵）、
可安全禁用候选仅 11。

GUI 依赖 WebView2 + Tauri 运行时，起不来就跑不了页面；而这一页恰好是
**数据合同最容易错**的地方 —— 后端把 148 个启动项、8 条开机记录按严格
JSON 形状交给前端，字段名差一个字母整页就白屏。

`tests/frontend_boot.mjs` 的做法：用**真机导出的 fixture**（不是手写假数据）
注入 `window.__TAURI__.core.invoke`，跑 **111 项断言**并截图。

它当场抓出 5 个真 bug（都是静态阅读看不出来的）：

| # | 现象 | 根因 |
|---|---|---|
| 1 | 整页白屏 | 后端返回 `Reply<T>`（`{ok,data,error}`），前端却直接读 `tl.records` / `scan.items` |
| 2 | 「拖慢开机 X s」永远不显示 | 归因回填只写在 CLI 里，IPC 层没调 `attach_impact` |
| 3 | 设置抽屉常驻、吃掉右侧点击 | `.drawer{display:flex}` 盖掉了 UA 的 `[hidden]{display:none}` |
| 4 | 刷新/提权按钮该藏不藏 | 同一个 `[hidden]` 问题，出在 `.btn{display:inline-flex}` 上 |

第 3/4 条是同一类问题，已在 `styles.css` 根部用一条

这类坑会反复咬人，不值得每个组件各写一遍。

复跑方式：

> **二轮补充的 7 组断言（第 9~15 组）** 覆盖的是「点得动、看得懂、退得回」：

> 不用 fixture 里的数字（前面的测试已经真的改过状态，用 fixture 数会差 2 项）。

## 七、延迟启动：想留但想更快（2026-10-15 补齐）

延迟启动（Delayed Autostart）与禁用是**两种用户意图**：禁用是「开机别再拉起它」，
延迟是「它还得在，但别挡道」。因此 UI 拆成两个按钮、两套确认文案，
后端也必须是两条执行路径。

### API 与边界

```rust
ChangeServiceConfig2W(
    svc,
    SERVICE_CONFIG_DELAYED_AUTO_START_INFO,          // = 3
    &SERVICE_DELAYED_AUTO_START_INFO { fDelayedAutostart: on.into() },
)
```

- 只对 **自动启动（Start=2）** 的服务有意义，其他启动类型直接拒绝并说明原因；
- 只对**服务**有效：注册表 Run 值 / 启动文件夹 / 计划任务没有等价能力，
  这些来源在 delay 模式下逐条返回「该来源不支持延迟启动」，不假装做了点什么；
- 设置**下次开机才生效**，不影响正在运行的服务；
- 同样走 SCM 而不是直接写注册表 —— 写注册表不会通知服务控制管理器。

### 撤销载荷的两种形态

| 动作 | undo 载荷 |
|---|---|
| 禁用 | `{"key":"<服务名>","start":2}` |
| 延迟 / 取消延迟 | `{"key":"<服务名>","delayed":true/false}` |

`undo_one` 按键位区分，两种载荷互不干扰。

### 为什么探针服务指向 `C:\Program Files-Zipz.exe`

`tests/service_write_verify.ps1` 建靶子服务时踩到两件事，都值得记下来：

1. 最初把 `binPath` 指到 `%SystemRoot%\System32\cmd.exe`，风险引擎判 **Dangerous** ——
   `assess_cheap` 对「位于系统目录的自动启动服务」一律保守，这是**正确行为**，
   测试靶子因此被自己的安全闸挡住了；
2. 把 `binPath` 改到 Program Files 下的已签名程序、显示名带上安全词（`updater`）后才通过。

顺带证明了一件事：**这套闸门对服务是真保守**，不是摆设。

### 真机实测（3 轮 + 1 轮禁用对照）

| 项 | 结果 |
|---|---|
| 延迟启动设置 | 3/3（注册表 `DelayedAutostart` 0→1） |
| 延迟回滚 | 3/3（回到 0） |
| 禁用→回滚 | 1/1（Start 2→4→2） |

脚本自建靶子服务、测完即删，测试产物写到 `%TEMP%\old666-write-verify`
（通过 `OLD666_DATA_DIR` 覆盖），不污染仓库与真实数据目录。

## 八、二轮返工：为什么「全选不好使」不是逻辑 bug（2026-10-15）

用户的原话是「全选不好使 —— 点了没反应/勾不上」。第一反应是去看事件绑定，
但绑定一直是好的。真正的根因是**几何**：

| 项 | 改前 | 改后 |
|---|---|---|
| 全选框结构 | 工具栏里一个裸 `<input type=checkbox>` | `<label class="chk">` 包住整块 |
| 全选热区实测 | 15 × 15 | **60 × 33** |
| 行内勾选热区高 | ~16 | **32** |
| 位置 | 落在首屏视口之外 | 在视口内 |

`.chk` 的写法（用负 margin 把视觉位置拉回去，热区留在外面）：

```css
.chk { display: inline-flex; padding: 7px 6px; margin: -7px -6px; min-height: 32px; }
.chk input { width: 16px; height: 16px; flex: 0 0 16px; }
```

**这条教训值得单独记**：只写「点了应该勾上」这类语义断言，
热区退回 15px 也照样能过。所以这一组断言**直接量 `getBoundingClientRect()`**，
`w >= 56 && h >= 28` 才算通过 —— 把「好不好点」变成可回归的数字。

同时把「全选」的语义钉死，并修掉一个真实的观感 bug：

- 全选 = 勾上**当前筛选内全部可勾选项**（不跨筛选、不勾不建议禁用的条目）；
- 之前切回「全部」时，全选框会**显示已全选但列表里有空勾** ——
  因为 `checked` 状态没跟着筛选重算。断言压成一句不变式：
  `全选框.checked === 可见可勾项.every(checked)`。

## 九、进程知识库：三层查找与「兜底条目」的纪律

目标：让每个开机自启项都能回答「它到底是干什么的」。
真机覆盖率 **89/148（60%）→ 142/148（96%）**。

查找按层降级，**逐层收窄**：

| 层 | 输入 | 说明 |
|---|---|---|
| ① 名称层 | 显示名 + exe 基名 | 最可靠，命中即返回 |
| ② 路径层 | `path_hint(command)` | 只取路径里到 `.exe` 为止的**厂商 / 产品目录段**，过掉 `program`/`files`/`system32`/版本号 |
| ③ 兜底层 | 宽通配（`updater` / `helper` / `push`） | **只在前两层全落空时**才允许命中 |

第三层的纪律是这个模块里最重要的一条：

```rust
// generic 条目命中后，建议被强制成「谨慎处理」——
// 一个叫 xxxlauncher 的程序到底是游戏启动器还是厂商推广位，
// 光看名字分不出来，说「可以禁用」是不负责任的。
```

三个层级都只认 `generic: false` 的条目，`generic: true` 的只在第三层生效；
且第三层若命中，`advice` 一律覆盖为「谨慎处理」。

### 二轮抓到的两个真误判（都已加回归测试）

1. **裸 key `launcher` 把《三角洲行动》启动器判成「可以禁用」**。
   `delta_force_launcher` 命中了 `launcher` → 用户点一下就把游戏搞坏。
   处理：删掉这个 key，并加 `bare_launcher_key_is_banned` 测试
   —— 以后谁再想加这种「太干净」的短词就会被CI拦下。
2. **重复 key 导致匹配不确定**：`fax` 出现两次、Defender 有两条 `nissrv`。
   处理：合并/删除，并加 `builtin_keys_do_not_collide_across_entries`
   遍历全库断言 key 全局唯一。

另外还有两个静默失效（不改也不报错，只是永远匹配不上）：

- `psspoolsv` 条目里那条 `fax` 是拼写残留；
- **`mddiagnosticscleanup` 少了一个 `m`**（MDM = Mobile Device Management），
  靠一个临时探针测试才发现，探针用完即删。

### 词边界：`contains_word` 而不是 `contains`

内置库里有 `node`、`time`、`qq` 这类短词。裸包含会让
`RuntimeBroker` 命中 `time`、`nodejs-helper` 命中 `node`。
词边界要求命中片段**前后都不是字母数字**。

顺带一个反直觉的坑：`path_hint` 早期把命令行**开关**也当成路径段了 ——
`foo.exe /clean` 会抽出 `clean` 这个目录名。修正为**在第一个 `.exe` 处截断**。

### 用户可编辑（对应「未知进程用户可以手动编辑其信息」）

- **用户库**：`data/knowledge/startup.json`，**外置可编辑**，
  **优先级高于内置库** —— 这正是「内置库里写错/没收录」的就地纠正手段，
  而且升级程序不会覆盖用户的补充。
- 交互：列表每行有「说明」按钮 → 打开面板 → 「编辑」→
  填匹配串/标题/厂商/描述/建议 → 保存。
- 「恢复内置说明」= 调 `knowledge_remove` 删掉用户条目，内置版本自动生效。
- 内置库本身随程序升级（源文件 `src-tauri/src/core/knowledge/builtin.json`）。

## 十、白名单 / 黑名单：两种截然相反的用户意图

外置文件：`data/startup_lists.json`（`whitelist` / `blacklist`，可直接编辑）。

| 名单 | 含义 | 行为 |
|---|---|---|
| **白名单** | 「这个我要留」 | 从「推荐禁用」里摘出去，仍可手动勾选 |
| **黑名单** | 「这个我要关，别再问我」 | **免二次确认，加入即禁用** |

黑名单免确认是用户明确要求（「加入黑名单的不需要过问直接禁用」）。
它不是绕过安全闸，而是**换个地方表态**：用户在说明面板里点「加入黑名单」
这个动作本身就是确认，再弹一次确认框属于重复打扰。
后端在 `planChanges` 里对黑名单条目放行风险档拦截。

**匹配方式（一个真实踩坑点）**：名单按名称匹配，但必须
**同时匹配「显示名」与「exe 基名」**（`hits()`）——
用户填了 `ollama`，而条目的显示名是 `Ollama Server`，
只用显示名匹配就会「加进去了却什么也没发生」。回归测试
`list_matches_the_exe_name_not_just_the_display_name`。

## 十一、禁用后「留在列表」与单条启用

用户明确选择了**「保留在列表，可一键启用」**，而不是从列表里消失。
这件事在四个来源上的实现成本完全不同：

| 来源 | 禁用手段 | 条目会消失吗 | 怎么留在列表里 |
|---|---|---|---|
| 注册表 Run | `StartupApproved\Run` 二进制标志 | 否 | 原地改标志位（`0x02` 启用 / `0x03` 禁用），一劳永逸 |
| 启动文件夹 | 移入隔离目录 | 是 | 同上，但我们保留记录后重建 |
| 自动服务 | `Start == 4` | **是**（枚举条件就是 `Start == 2`） | `merge_disabled_by_us()` 按变更记录重建 |
| 计划任务 | `<Enabled>false</Enabled>` | **是**（只枚举 Boot/Logon 触发器） | 同上 |

`merge_disabled_by_us()` 是这里的关键：它读我们自己的变更记录，
把「被我们禁掉的、但已经不在枚举结果里」的条目**补回列表**，
带上「老六禁用」徽标，并提供行内「启用」按钮。

**单条启用不弹确认框**：启用是**非破坏性**动作，风险闸不需要参与。

```rust
fn needs_risk_gate(&self) -> bool {
    !matches!(self, Mode::Enable)   // Enable 永远不过闸
}
```

这是有意为之：让用户「退回去」的路径尽可能短。
反方向的「禁用」才需要 `startup_plan` 演练 + 确认。

## 十二、删除：只对能安全删的来源开放

「注册表项支持删除，删除前要进行备份」—— 落地时把范围收得更紧了：

| 来源 | 允许删除 | 理由 |
|---|---|---|
| 注册表 Run / RunOnce | ✅ | 就是一条值，删了干净；原值已备份 |
| 启动文件夹 | ✅ | 就是一个 `.lnk` |
| 自动服务 | ❌ | 删掉会伤系统（注册表键删了但 SCM 还在，状态会不一致），明确提示改用「禁用」 |
| 计划任务 | ❌ | 同上，提示改用「禁用」 |

不可删的来源在说明面板里**按钮置灰 + 给出替代方案**，
而不是让按钮点了没反应。文案：

> 这个来源不支持删除自启（删掉会伤系统），请改用「禁用」—— 同样可随时启用回来。

删除前自动备份原值并写进「变更记录」，可整体还原
（与禁用的撤销载荷共用一条回滚链路）。

## 十三、对标 360 安全卫士启动项管理的功能覆盖

360 的启动项管理是这一领域的用户心智基线，逐条对照如下：

| 360 的功能点 | 老六清净 | 差异说明 |
|---|---|---|
| 四类启动项列举（注册表 / 文件夹 / 服务 / 任务） | ✅ 148 项 | 一致 |
| 开机时间与「拖慢了多久」 | ✅ 归因误差 0% | 360 是估算，我们是读 Windows 自报数字 |
| 每项「是什么 / 该不该关」的中文说明 | ✅ 173 条内置 + 用户可编辑 | 覆盖率 96%，未知项用户可自己写 |
| 一键禁用 / 启用 | ✅ | 禁用前出示演练清单（360 直接执行） |
| 延迟启动（服务） | ✅ | `ChangeServiceConfig2W`，走 SCM |
| 启动项白名单 | ✅ | |
| 「禁止启动」黑名单（免确认） | ✅ | |
| 恢复 / 回滚 | ✅ 批次 + 单条 | 撤销载荷自包含，换机器也能还原 |
| 删除启动项 | ✅ 仅安全来源 | 删除前自动备份 |
| 开机时间历史趋势 | ✅ 最近 8~50 次 | |
| 云查杀 / 木马库 | ❌ 不做 | 不是本产品的定位；但把「可疑特征」降级为「谨慎」，不冒充杀软 |

**刻意不做的**：不猜、不编、不夸大。「优化后可省 XX 秒」这类无法验证的数字一律不给 ——
我们的原则是「宁可少关，不可错关」，以及 UI 上只显示能自证的数据。

## 十四、列表排序与折叠：把「找」这件事从用户手里拿走（v0.1.3）

用户的原话是「默认把推荐禁用的放在列表前面，已经禁用的支持隐藏」。
背景是上一版修完「可安全禁用却选不中」之后暴露出的真问题：
真机 143 项里只有 28 项可勾，剩下 31 项已禁用、84 项不建议禁用，
全部按系统原始顺序混排 —— 用户要在 143 行里自己找出那 28 行。

### 14.1 四档排序，稳定且可解释

```js
function displayRank(it) {
  if (recommended(it)) return 0;   // 推荐禁用：值得动手
  if (pickable(it))    return 1;   // 可勾选：能动手
  if (it.enabled)      return 2;   // 不建议禁用：只看不动
  return 3;                        // 已禁用：已经关掉了
}
```

排序在 `visibleStartups()` 里做，**稳定**（`sort` 比较器返回 rank 差值，
V8 的 `Array.prototype.sort` 自 ES2019 起保证稳定，同档内保持系统原序）。
不用「rank 拼 id」这类技巧，是因为它会随 id 变化而抖动 ——
用户第二次扫描看到顺序变了，会以为数据出问题。

为什么「已禁用」排最后而不是排最前：这一档是**已经处理完的**，
用户来这里是为了「还能做什么」，不是「我做过了什么」。
想找它们要么往下翻，要么直接开「隐藏已禁用」。

### 14.2 折叠要藏得住，也要说得清

「隐藏已禁用」写在筛选栏右侧，状态存 `localStorage`：

```js
function readHidePref() { try { return localStorage.getItem('old666.hideDisabled') === '1'; } catch { return false; } }
```

- **不能只是 CSS 隐藏**：被折叠的行不参与「全选」计数、不参与搜索命中，
  所以过滤发生在 `visibleStartups()` 里，而不是渲染后加 class。
- **少了多少行要说**：副标题追加 `· 已隐藏 N 项已禁用`。
  143 → 112 行时如果不说明，用户会怀疑「是不是漏扫了」。
- **展开不跳过校验**：折叠期间新露出的行可能还没补签名，展开时若还有未补签
  条目就重跑一次 `verifyStartup()`，不能因为「刚才藏过」就把「正在确认发布者…」
  永远停在待定态。
- **持久化但可失效**：`localStorage` 在便携场景下跟着 WebView2 的用户数据目录走；
  读失败（隐私模式 / 目录只读）就退回默认「不隐藏」，不抛错。

### 14.3 只改显示，不改判定

排序和折叠都只作用于 `visibleStartups()` 的输出，**不碰扫描结果**，
也不改变 `pickable()` 的结论。断言里因此没有断「第一行是什么名字」，
而是断「`data-rank` 序列非递减」—— 后者与数据内容解耦，fixture 换了也成立：

```
✓ 整张表按「推荐 → 可勾选 → 不建议 → 已禁用」排列
  — 000000001111111111111111111122222222…3333333333333
```

同组还有一条容易漏的：**隐藏后的行数必须等于隐藏前的行数减去 DOM 里的 `off` 行数**，
而不是减去 fixture 里标的已禁用数 —— 前面的用例已经真的禁用过几项，
fixture 的数字早就过期了。这条差 2 项时被断言当场抓住。

## 十五、「优化后开机实测对比」：数据源停更了，以及替代口径（2026-11-06）

实施计划里最后一条没打勾的验收项是「优化后开机时间有可测量的缩短」。
补这一条时先撞上一个不在预期内的坑。

### 15.1 坑：性能日志写满了，而且不自愈

`Microsoft-Windows-Diagnostics-Performance/Operational` 通道一直 enabled，
`old666-poc --boot` 读的就是它。2026-11-06 查的时候发现：

| 项 | 值 |
|---|---|
| 通道状态 | enabled=true，type=Operational，maxSize=1052672 |
| 日志文件大小 | **1052672 字节（正好等于 maxSize）** |
| 文件最后写入 | 2026/10/20 13:15:32 |
| 事件 100 最新一条 | 2026/10/20 13:14:36（此前 50 条覆盖 08-20 → 10-20） |

也就是说：**日志被写满了，但没滚动，Windows 也就没再写新记录**。
同一时期 System 日志的 6005（事件日志服务已启动）一直正常产生到 11-06，
机器关机/开机一切正常 —— 缺的只是这一个通道的写入。

排查过的方向（都不是原因）：

- `HKLM\SYSTEM\CurrentControlSet\Control\WINEVT\Channels\...` 注册表键在 `reg query` 下「找不到指定的注册表项或值」——**这其实是正常的**，通道配置由事件日志服务自己维护，注册表里本来就不落这个键；
- `WindowsErrorReporting\Diagnostics` 不存在、`Policies\...\WindowsErrorReporting` 不存在 —— 与本问题无关；
- `HiberbootEnabled=1`（快速启动）—— 理论上会影响事件 100 的记录语义，但**实测快速启动期间的事件 100 一样正常**，排除。

### 15.2 修复：把通道清空并放大上限

```
wevtutil sl "Microsoft-Windows-Diagnostics-Performance/Operational" /ms:8388608   # 1MB → 8MB
wevtutil cl "Microsoft-Windows-Diagnostics-Performance/Operational"                # 清空
```

清空后文件从 1052672 → 69632 字节，通道已可写入（需下一次重启才会产生新的事件 100）。
旧数据**没有丢**：清空前先把 `.evtx` 复制到 `%TEMP%\dperf-backup.evtx`，
`Get-WinEvent -Path` 仍能读到其中全部 706 条事件（含 50 条事件 100）。
（`wevtutil epf` / `rp` 在本机不支持导出/回灌，所以只能整体拷文件。）

### 15.3 替代口径：拿不到事件 100 时，用 System 日志的 12 与 6005 差值

事件 100 停更期间，我们仍然有 System 日志里的两个可靠锚点：

- **事件 12**「操作系统已在系统时间 … 启动」—— 内核层面的启动时刻；
- **事件 6005**「事件日志服务已启动」—— 用户态服务起来、系统基本可用的时刻。

两者差值 = **从内核启动到事件日志服务可用**的秒数。这是一个偏「核心启动路径」的
口径，比事件 100 的 BootTime 短（BootTime 还包含 post-boot 阶段），但**两侧口径一致**，
足够回答「优化前后有没有可测量的缩短」。

按此口径统计本机 52 轮启动（2026-09-09 → 11-06）：

| 分组 | 样本 | 中位 | 均值 | 最小 | 最大 |
|---|---|---|---|---|---|
| 优化前（09-09 ~ 10-20 18:51） | 46 | **15.5 s** | 15.7 s | 12.8 s | 20.9 s |
| 优化后（10-21 起） | 6 | **13.3 s** | 13.7 s | 13.0 s | 15.5 s |

优化后逐轮明细：

| 开机时刻 | 秒 |
|---|---|
| 10-21 03:04 | 15.5 |
| 11-04 12:57 | 14.1 |
| 11-04 16:06 | 13.1 |
| 11-04 17:33 | 13.0 |
| 11-05 21:44 | 13.2 |
| 11-06 10:08 | 13.3 |

**读法**：核心启动路径中位数从 15.5 s 降到 13.3 s，约 **2.2 s**。

### 15.4 这个结论该被怎么表述 —— 以及不能怎么表述

优化动作发生在 **10-20 18:51**（v0.1.1 期间给 9 个服务设了延迟启动，
批次文件 `data/startup/sb-*.json`），分界点取的就是这个时刻。

必须说清楚的边界：

1. **样本量小**：优化后只有 6 轮，且集中在 11-04/11-05/11-06 三天。
2. **变量不干净**：同期还有用户自己关掉的注册表启动项（doubao / LM Studio / 剪映 / MuMu / Steam / 迅雷 等 8 项 `enabled=false`），**不全是 old666 干的**。
   old666 自己禁用的项目前是 **0**（`disabled_by_us` 计数为 0），延迟启动 9 项。
3. **口径不同**：这不是事件 100 的 BootTime，是「内核启动 → 日志服务可用」。
4. **不能反推因果**：2.2 s 的差里，有多少来自延迟启动、有多少来自用户自己关的东西、
   有多少只是系统状态波动（如当时后台装的软件），**无法拆分**。

所以结论只能这么写：

> 在「内核启动 → 事件日志服务可用」这一口径下，2026-10-20 傍晚应用 9 项延迟启动
> 之后，本机 6 轮开机的中位耗时为 13.3 s，此前 46 轮的中位为 15.5 s。
> **该差值与优化方向一致，但样本量与变量控制不足以归因给 old666。**
> 事件 100 通道已修复，下次重启后即可恢复精确口径（BootTime / MainPathBootTime /
> BootPostBootTime 与分段归因），届时可重新采集一轮做严格对比。

这条「可测量的缩短」验收项，**只能标成「有方向性证据，未完成严格验证」** ——
不编数字，不把相关当因果。这与 `docs/P2-开机加速-技术说明.md` 开篇
「刻意不做的：不猜、不编、不夸大」是同一条纪律。
